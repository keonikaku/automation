What is and isn't on this page

  • Two videos, not a reel of clips. The web walkthrough is one continuous browser session driven end to end; the second is a screen capture of an iPhone Simulator while Appium drives the app. Both are unedited and neither is sped up or cut.
  • The suite and the recording are separate programs, on purpose. The tests in tests/ui/ each get a fresh browser context, because isolation is the point — a test that inherits another test's session isn't testing what it claims. That is what CI runs. A recording needs the opposite, so a separate runner in demo/ drives the same page objects through one session in an order that reads as a story. Same code, sequenced differently. The suite was not loosened to make a nicer video.
  • The assertion under each step is the real line from tests/ui/. They read as page-object calls — contact.success_message rather than a CSS string — because selectors live in shopsmart/pages/ and nowhere else. Unit tests fail the build if a raw selector appears in a test file, or if a line quoted on this page drifts from the suite.
  • The walkthrough is deliberately slowed. Playwright at full speed is unreadable, so the recorder runs with a fixed delay between actions. That is a recording choice and nothing on this page presents a duration as a measurement.
  • Recorded headless — the same way it runs unattended. The suite defaults to headless and takes --headed when a human wants to watch.
  • A build server checks the repository, not this page. The CI workflow gates lint, unit tests and collection integrity on every commit; the live web suite runs on a nightly schedule and is reported rather than gated, because it drives a third-party practice site that can go down for reasons no commit here controls. The reasoning is written up in quality-gates.md. The videos here are a recording of one local run on a stated date, not a live status.
  • No audio and no cursor overlay — the capture is the browser viewport and the device screen, which is why input focus and page transitions are the only visible signal.

web walkthrough Playwright All steps passed

One browser session from a rejected login through to an empty search result — no relaunch between steps. Produced by demo/record_web_walkthrough.py, which drives the same page objects the test suite uses.

01 test_08_invalid_login Negative

A login that has to fail. The address was never registered, so the site must reject it rather than fail open.

expect(login_page.error_message).to_be_visible()
02 test_01_login Happy path

The same form, with credentials that work. The account is registered by the run itself moments earlier, in a separate browser context, and deleted afterwards — so this depends on nothing that existed before the run started.

expect(page).to_have_url(f"{settings.base_url}/") expect(login_page.logged_in_banner).to_contain_text(registered_account.name)
03 test_02_search Happy path

Search the catalogue and verify results actually came back — not merely that a results heading rendered.

expect(products.results_heading).to_be_visible() assert products.result_count() > 0
04 test_03_filter_by_category Happy path

Load the Women › Dress category directly. The practice site injects ads over the nav, so a click path there would test the ad network rather than the site.

expect(category.heading).to_be_visible() assert category.current_url == category.url
05 test_04_add_to_cart Happy path

Add the first product, follow the confirmation modal's View Cart link, and verify the browser lands on the cart.

expect(page).to_have_url(cart.url)
06 test_05_checkout_requires_login Negative

Checkout as a guest must be blocked. The walkthrough signs out first — it logged in at step 2, and a logged-in user is correctly not blocked, so the gate would never appear. Showing the sign-out on camera is the honest way to reach it.

expect(cart.login_required_prompt).to_be_visible()
07 test_06_contact_form Happy path

Fill and submit the contact form, then verify the success banner. The form fires a native confirm dialog, so the page object arms a handler before clicking — an unhandled dialog blocks Playwright and the test would hang rather than fail.

expect(contact.success_message).to_be_visible()
08 test_10_search_no_results Negative

A term with no matches must return an empty grid. The count is the load-bearing assertion: the heading renders either way, so checking only the heading would pass even if the site returned the whole catalogue.

expect(products.results_heading).to_be_visible() assert products.result_count() == 0

SMART-201 — one defect, traced through 4 cases into the smoke suite

Search ignored the active category filter: filter to Women, search, and results came back from every category. Rather than log it and move on, the issue was traced into coverage — CAT-16, CAT-17 and CAT-18 pin the behaviour from different angles, and the smoke suite is this one case. A one-case smoke suite is a decision, not a thin result: smoke exists to answer “is this build worth testing?”, and the fastest honest answer here was the regression most likely to make the catalog useless.

SMOKE-01 SMART-201 Automated: No

Smoke — Search respects active category filter (SMART-201)

Preconditions
User is on the All Products page.
Steps
  1. Click on Women category in the left sidebar.
  2. Enter any valid search term in the search bar.
  3. Click the Search button.
  4. Observe the search results.
Expected result

Search results contain only Women's products matching the search term. Products from other categories are not displayed.

Priority / Type
Critical · Smoke

Designed, prioritised Critical, and not automated. Nothing in the suite yet combines a category filter with a search. It sits in the backlog — an ordinary state for real work, and more useful published honestly than quietly closed.

All 54 cases, and the files

9 of 54 cases have automated coverage — 6 fully, 3 partially. The other 45 are designed and run manually, which is the point rather than a shortfall: test design and automation are different activities, and which cases get automated is a risk decision. The 19 “spec gap” rows are finished cases, not blank ones — where the specification was silent, the case records that and proposes an expectation instead of inventing one and turning a guess into the standard the build gets measured against.
