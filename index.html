What is and isn't on this page

  • All 10 web tests in tests/ui/ are recorded here, and all 10 passed on this run. The one test with no recording, and why, is listed at the bottom of the page — it is not hidden.
  • The assertion shown under each video is the real line from tests/ui/. They read as page-object calls — contact.success_message rather than a CSS string — because selectors live in shopsmart/pages/ and nowhere else. A unit test fails the build if a raw selector appears in a test file.
  • These recordings are automatic, not curated for looks. A pytest fixture in tests/conftest.py hands each test a browser context configured for video and closes it afterwards, so a run records itself. Failing tests get recorded the same way passing ones do.
  • This run was headless — the same way it runs unattended. The suite defaults to headless and takes --headed when a human wants to watch it.
  • A build server checks the repository, not this page. The CI workflow gates lint, unit tests and collection integrity on every commit; the live web suite runs on a nightly schedule and is reported rather than gated, because it drives a third-party practice site that can go down for reasons no commit here controls. The reasoning is written up in quality-gates.md. The videos above are a recording of one local run on a stated date, not a live status.
  • The videos have no audio and no cursor overlay — Playwright records the browser viewport only, which is why input focus and page transitions are the only visible signal.

The runs

10 videos · ~1.1 MB total · recorded 2026-07-28
test_01_login Happy path Pass

Logs in with valid credentials and verifies the site returns an authenticated session.

expect(page).to_have_url(f"{settings.base_url}/") expect(login_page.logged_in_banner).to_contain_text(registered_account.name)

The account is created by the test run itself. A fixture registers a throwaway account before the test and deletes it afterwards, in a separate browser context so the test still has to log in for real. This test was previously dead — it depended on one hand-made account on a public practice site, and it stopped working the day that account was deleted.

test_02_search Happy path Pass

Searches the product catalogue for dress and verifies the results page renders and actually returns matches.

expect(products.results_heading).to_be_visible() assert products.result_count() > 0
test_03_filter_by_category Happy path Pass

Loads the Women › Dress category and verifies the correct category page is served.

expect(category.heading).to_be_visible() assert category.current_url == category.url

Navigates straight to the category URL rather than clicking through the menu — the practice site injects ads over the nav, and a click path there tests the ad network, not the site.

test_04_add_to_cart Happy path Pass

Adds the first product to the cart, follows the confirmation modal's View Cart link, and verifies the browser lands on the cart page.

expect(page).to_have_url(cart.url)
test_05_checkout_requires_login Negative Pass

Adds an item as a guest and attempts checkout, verifying the site blocks it and demands an account instead of letting an unauthenticated order through.

expect(cart.login_required_prompt).to_be_visible()
test_06_contact_form Happy path Pass

Fills and submits the contact form, then verifies the success banner appears.

expect(contact.success_message).to_be_visible()

The form fires a native browser confirm dialog on submit. The page object arms a dialog handler beforehand — page.on("dialog", …accept()) — because an unhandled dialog blocks Playwright and the test would hang rather than fail cleanly.

test_07_mobile_login Mobile web Pass

The same login flow under Playwright's iPhone 13 device emulation — viewport, user agent and touch support — verifying the mobile layout authenticates the same way the desktop one does.

expect(mobile_page).to_have_url(f"{settings.base_url}/") expect(login_page.logged_in_banner).to_contain_text(registered_account.name)

Registers and deletes its own account, like test_01_login. The narrow viewport in the recording is the emulated device, not a resized window.

test_08_invalid_login Negative Pass

Attempts login with an address that was never registered and verifies the site rejects it with the expected error rather than failing open.

expect(login_page.error_message).to_be_visible()

Self-contained by design: the fake address is hardcoded in the test, not read from the environment. A negative-path test that needs real credentials to run is a test that stops working the moment the account does.

test_09_empty_login_fields Negative Pass

Submits the login form with both fields empty and verifies the browser stays on the login page — field validation blocks the submit.

expect(page).to_have_url(f"{settings.base_url}/login")
test_10_search_no_results Negative Pass

Searches for a term with no matches and verifies the results grid actually comes back empty.

expect(products.results_heading).to_be_visible() assert products.result_count() == 0

The count is the load-bearing assertion. The “Searched Products” heading renders whether or not anything matched, so a test that checked only the heading would pass even if the site returned the entire catalogue — which is exactly what this test used to do.
